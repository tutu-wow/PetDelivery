# 宠物上门服务小程序

> AI 宠物问答 · WebSocket 即时聊天 · 余额支付与退款 · 服务订单状态流转 · 服务过程反馈 · 服务评价与词云分析 · ECharts 运营数据分析

身边养宠物的同学都碰到过同一件麻烦事：临时要出差、加班回不去，狗子必须遛、猫要上门喂，找谁去？问朋友欠人情，找陌生人又不放心——资质看不出来、服务好不好全靠运气、出了问题还不好追溯。

这套系统就顺着"把上门服务做成一笔能查、能管、能追责的订单"的思路做：先建宠物档案，再挑服务项目和服务人员，在线预约、余额支付、接单上门、过程反馈、评价结算一条线走完；服务人员有自己的工作台，管理员在后台盯订单、评价和运营数据。对做毕设的同学来说，这条"多方协作 + 状态流转"的主线，比单纯堆增删改查有讲头得多。

---

## 一、项目简介

宠物上门服务平台采用前后端分离架构，面向用户、服务人员和管理员提供协同服务。系统围绕宠物档案、服务项目浏览、服务人员筛选、在线预约、余额支付、订单履约、过程反馈、服务评价、消息沟通及运营分析构建完整链路；管理端集中提供用户、服务资源、订单、评价、内容与统计数据的维护能力。

## 二、功能亮点

| 亮点 | 实现要点 |
| :--- | :--- |
| AI 宠物问答 | 面向宠物护理、健康、饮食、训练与品种等场景，保存会话与消息，组合系统提示词、历史消息和当前问题调用模型，支持 SSE 流式输出 |
| WebSocket 即时聊天 | 消息先落库并记录发送方、接收方、内容、类型与已读状态，接收方在线时通过 WebSocket 定向推送，会话列表与历史消息可查 |
| 余额支付与退款 | 下单时校验账户余额，生成以 `SO` 开头的订单号、同步扣减余额并写入消费流水；待确认或已确认订单取消时退回余额并记录退款流水 |
| 服务订单状态流转 | 以状态机控制履约：待确认 → 已确认 → 服务中 → 待确认完成 → 已完成，各操作先校验当前状态再允许流转，已取消订单单独归集 |
| 服务过程反馈 | 服务人员按订单发布进度，保存标题、图片与服务时间；用户查看后标记已读并记录阅读时间，按服务时间倒序展示 |
| 服务评价与信誉统计 | 评价仅限已完成订单提交且一单一评；保存后重算服务人员平均评分与累计完成订单数，并向服务人员推送通知 |
| 词云分析 | HanLP 对评价文本分词，过滤停用词与无效词性，按词频取前 80 项，用于评价词云展示 |
| ECharts 运营数据分析 | 汇总订单、收入、用户、服务人员与宠物数量，输出趋势、状态分布、项目与人员排行，以及评分分布、满意率和评价趋势 |
| 权限控制与操作审计 | 登录签发 JWT，拦截器解析用户身份与角色写入请求上下文；关键操作由 AOP 成功后自动记录操作人、模块、动作、详情与 IP |

## 五、核心实现说明

### 5.1 宠物档案、服务浏览与服务人员筛选

系统以宠物档案和服务资源为预约基础。用户可维护宠物名称、品种、年龄、体重、性别、绝育情况、健康信息、特殊需求及照片；在服务端浏览服务类型与服务项目，并按服务项目、服务区域、擅长品种和服务人员状态筛选服务人员。服务人员资料包含个人简介、资质证书、从业年限、可服务区域、可提供项目、综合评分和累计完成订单数，用户可将服务人员加入收藏。

```
维护宠物档案 → 浏览服务类型与服务项目 → 按服务能力、区域或品种筛选服务人员 → 查看详情与历史评价 → 收藏或进入预约下单
```

| 业务场景 | 系统处理结果 |
| :--- | :--- |
| 宠物档案 | 保存所属用户、品种、年龄、体重、健康信息、特殊需求及图片，为下单和服务执行提供宠物信息 |
| 服务资源 | 服务项目关联服务类型，维护适用品种、服务内容、价格、时长、注意事项和图片，支持用户端浏览与管理端维护 |
| 服务人员筛选 | 按姓名、擅长品种、服务区域、可提供项目、审核状态及人员状态组合查询候选服务人员 |
| 服务人员收藏 | 记录用户与服务人员的收藏关系，用户可在个人中心查看或取消收藏 |

### 5.2 预约下单、余额支付与退款流水

用户预约时选择服务项目、宠物档案、服务人员、上门地址、服务日期及备注。提交订单时，服务端校验下单用户和订单金额，确认账户余额充足后生成以 `SO` 开头的订单号，将订单状态设为"待确认"，同步扣减余额并写入消费流水；若订单在待确认或已确认阶段取消，则订单状态改为"已取消"，金额退回余额并写入退款流水。

```
选择项目、宠物、人员、地址与日期 → 校验余额 → 创建待确认订单 → 扣减余额并记录消费流水 → 通知服务人员接单 → 可取消订单并回退余额、记录退款流水
```

| 业务场景 | 系统处理结果 |
| :--- | :--- |
| 创建订单 | 余额足够时写入订单、订单号和待确认状态，同时维护用户余额与消费流水；余额不足时返回提示，不创建订单 |
| 地址管理 | 用户可维护联系人、联系电话及上门地址，订单通过地址记录关联服务地点 |
| 取消与退款 | 待确认或已确认订单允许取消，系统更新订单状态、退回订单金额、记录退款前后余额并通知对应服务人员 |

### 5.3 服务订单状态流转、进度反馈与消息通知

订单履约采用状态机控制服务过程。服务人员仅能对待确认订单接单，接单后将状态更新为已确认；已确认订单可开始服务并记录实际开始时间；服务中订单可标记完成并记录实际结束时间，进入待确认完成；用户确认后订单才变为已完成。每次状态变化均向相关用户创建订单通知。服务人员还可按订单发布文字标题、图片和服务时间构成的服务进度，用户查看后可将进度标记为已读并记录阅读时间。

```
待确认 → 服务人员接单 → 已确认 → 开始服务 → 服务中 → 服务人员标记完成 → 待确认完成 → 用户确认 → 已完成
```

| 状态对象 | 状态与处理 |
| :--- | :--- |
| 订单状态 | 支持待确认、已确认、服务中、待确认完成、已完成和已取消；各操作均校验当前状态后才允许流转 |
| 服务进度 | 进度记录关联订单和服务人员，保存进度标题、图片、服务时间、已读状态和阅读时间，按服务时间倒序展示 |
| 订单通知 | 下单、接单、开始服务、完成服务、确认完成和取消订单等动作会生成关联订单的通知，供消息中心查看 |

### 5.4 服务评价与服务人员信誉统计

评价仅允许由已完成订单提交，同一订单只能评价一次。用户可提交评分、文字内容及图片；评价保存后，服务端重新汇总该服务人员的有效评分，更新平均评分和已完成订单数，并创建"收到新评价"的通知。评价数据既在服务人员详情中作为服务参考，也为管理端评价分析提供输入。

```
用户确认订单完成 → 校验订单状态与是否已评价 → 保存评分、文字及图片 → 重算服务人员平均评分和累计完成订单数 → 通知服务人员
```

| 校验或统计项 | 系统处理结果 |
| :--- | :--- |
| 评价资格 | 订单不存在、未完成或已存在评价记录时，系统拒绝重复或不符合条件的评价提交 |
| 平均评分 | 按服务人员名下评价的评分求平均值，并保留一位小数更新到服务人员资料 |
| 累计订单 | 统计该服务人员状态为已完成的订单数量，更新为累计完成订单数 |

### 5.5 WebSocket 在线聊天与 AI 宠物问答

系统提供用户间的在线聊天和面向宠物护理场景的 AI 问答。聊天消息先保存发送方、接收方、内容、类型、发送时间及已读状态；接收方在线时，服务端通过 WebSocket 将消息推送到指定用户，同时保留消息记录供会话列表和历史消息查询。AI 问答以宠物护理、健康、饮食、训练和品种等问题为主要范围，系统保存会话和消息，并将系统提示词、历史消息和当前问题组成上下文调用外部模型；接口支持 SSE 流式返回和适配小程序的同步返回。

```
发送聊天内容 → 消息落库 → 判断接收方在线状态 → WebSocket 定向推送 → 会话列表与历史记录查询
```

```
创建或选择 AI 会话 → 保存用户问题 → 组合系统提示词与会话历史 → 调用模型 → 流式或同步返回回答 → 保存助手消息并更新时间与摘要
```

| 能力 | 实现方式 |
| :--- | :--- |
| 即时聊天 | 连接按用户 ID 保存；消息通过 HTTP 创建并持久化后，使用 WebSocket 向指定在线接收者推送 JSON 消息 |
| AI 会话管理 | 首次提问自动创建会话并以问题内容生成标题；会话按最后消息时间排序，删除会话时同步删除其消息 |
| AI 流式响应 | 接口以 `text/event-stream` 返回会话标识和生成片段，模型完成后发送结束标识；生成结果会保存为助手消息 |

### 5.6 管理端运营维护、权限控制与操作审计

系统角色分为管理员、普通用户与服务人员。后端在登录后生成 JWT，拦截器从请求头解析用户 ID 和角色并写入当前请求上下文；前端通过 Pinia 保存登录态及角色信息，并结合路由守卫限制管理端访问。管理端覆盖用户、服务人员、服务类型、服务项目、宠物档案、服务区域、订单、评价、轮播图、公告、通知、余额流水和操作日志等数据维护。对新增、修改、删除、取消、确认、接单、审核、开始服务、下单和提交等关键操作，AOP 在接口成功返回后自动记录操作用户、模块、动作、详情及 IP 地址。

```
用户登录 → 生成 JWT → 请求携带 Authorization → 拦截器解析身份 → 前后端按角色控制页面与业务入口 → 关键操作成功后自动写入审计日志
```

### 5.7 订单与评价数据分析

管理端使用 ECharts 和词云扩展展示订单与评价分析结果。订单分析汇总订单、已完成订单、已取消订单、进行中订单、平台收入、用户、服务人员和宠物数量，并按日期、状态、服务项目、服务人员和月份形成趋势、分布及排行数据；其中平台收入仅统计已完成订单金额。评价分析提供评价总数、平均评分、五星数、满意率、带图评价数、评分分布、近 7 天与近 6 个月趋势、服务人员评分排行、服务项目评分排行和评价词云。词云由 HanLP 对评价内容分词，过滤停用词及无效词性后统计高频词并返回前 80 项。

```
订单与评价数据 → 后端聚合统计与文本分词 → 输出趋势、占比、排行和词云数据 → ECharts 渲染管理端数据看板
```

| 分析主题 | 统计维度 |
| :--- | :--- |
| 订单分析 | 近 7 天订单趋势、订单状态分布、服务项目订单排行、服务人员接单排行、近 6 个月订单量与已完成订单收入趋势 |
| 评价分析 | 评分分布、评价数量与平均评分趋势、服务人员与服务项目评分排行、满意率、带图评价数量及评价词云 |
| 词云处理 | 对评价文本进行 HanLP 分词，仅保留长度不少于 2 的名词、动词和形容词，排除停用词后按词频倒序取前 80 项 |

## 八、适合谁

- 想做**选题接地气**的毕设：宠物上门是近年真实需求，选题动机一句话讲得清
- 想体现**多角色协同**能力的同学：用户下单、服务人员履约、管理员运营，三方围绕同一订单协作
- 想讲清**状态流转**的同学：订单从待确认到已完成的状态机完整，每一步都有校验和通知
- 想加**AI 与实时能力**的同学：DeepSeek 流式问答 + WebSocket 定向推送，技术上和普通增删改查拉开差距
- 需要**数据可视化落点**的场景：ECharts 趋势、分布、排行图 + 词云，论文有图有数据
- 想练**前后端分离**的同学：Controller／Service／Mapper 分层 + JWT + AOP 审计，接口与鉴权链路清晰
